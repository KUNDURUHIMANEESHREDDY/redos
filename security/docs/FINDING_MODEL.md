# Finding Model Specification

## Overview

The Finding model is the core output of the security analysis pipeline. Every finding must be traceable to actual evidence and follow a strict lifecycle.

## Finding Structure

```python
class Finding(BaseModel):
    id: UUID                          # Unique finding identifier
    target_id: str                    # Target system identifier
    attack_id: str                    # Attack identifier
    execution_id: UUID                # Reference to execution that produced evidence
    vulnerability_type: VulnerabilityType
    severity: SeverityLevel           # CRITICAL, HIGH, MEDIUM, LOW, INFO
    confidence: ConfidenceLevel       # LOW, MEDIUM, HIGH, VERY_HIGH
    impact: ImpactLevel               # NONE, LOW, MEDIUM, HIGH, CRITICAL
    exploitability: ExploitabilityLevel  # NONE, LOW, MEDIUM, HIGH, CRITICAL
    attack_path: AttackPath | None    # From attack graph construction
    evidence_ids: list[UUID]          # References to actual evidence (REQUIRED)
    root_cause: RootCause | None      # Root cause analysis result
    remediation: list[RemediationAction]  # Remediation steps
    reproduction: dict[str, Any]      # Reproduction steps
    regression_tests: list[RegressionTest]
    status: FindingStatus             # NEW, CONFIRMED, REMEDIATED, REGRESSION_TESTED, FIXED
    risk_score: float                 # 0.0 - 10.0
    cvss_vector: str | None           # CVSS vector string
    cvss_score: float | None          # Base CVSS score
    tags: list[str]
    metadata: dict[str, Any]
    created_at: datetime
    updated_at: datetime
    closed_at: datetime | None
```

## Required Fields

| Field | Required | Description |
|-------|----------|-------------|
| id | Yes | Auto-generated UUID |
| target_id | Yes | Target system identifier |
| attack_id | Yes | Attack identifier |
| execution_id | Yes | Must reference valid execution |
| vulnerability_type | Yes | From VulnerabilityType enum |
| severity | Yes | Calculated via severity service |
| confidence | Yes | Assessment confidence |
| impact | Yes | Impact assessment |
| exploitability | Yes | Exploitability assessment |
| evidence_ids | **Yes** | **At least one required** |
| status | Yes | Defaults to NEW |

## Finding Lifecycle

```
NEW → CONFIRMED → REMEDIATED → REGRESSION_TESTED → FIXED
  ↓
FALSE_POSITIVE (terminal)
  ↓
WONT_FIX (terminal)
  ↓
DUPLICATE (terminal)
```

### Valid Transitions

| From | To (Valid) |
|------|------------|
| NEW | CONFIRMED, FALSE_POSITIVE, DUPLICATE |
| CONFIRMED | REMEDIATED, FALSE_POSITIVE, WONT_FIX |
| REMEDIATED | REGRESSION_TESTED, CONFIRMED |
| REGRESSION_TESTED | FIXED, REMEDIATED |
| FIXED | (terminal) |

## Evidence Requirements

**Every finding MUST have at least one evidence reference.**
- Evidence must exist in the evidence store
- Evidence must be in NORMALIZED or CORRELATED state
- Evidence IDs stored in `evidence_ids` list
- Used for traceability and verification

## Deduplication

Findings are automatically deduplicated per execution:
- Key: `target_id:vulnerability_type:attack_id`
- First finding = primary, subsequent = DUPLICATE
- Duplicate findings reference primary via `metadata["duplicate_of"]`

## Correlation

Findings sharing evidence are correlated:
- Detected via `correlate_findings(execution_id)`
- Returns shared evidence pairs with correlation type

## Severity Calculation

Severity is calculated via `SeverityCalculationService`:
1. Map finding attributes to CVSS v3.1 metrics
2. Calculate base, temporal, environmental scores
3. Convert final score to severity level
4. Store CVSS vector string and rationale

## Root Cause Analysis

Performed by `RootCauseAnalyzer`:
- Analyzes evidence to determine root cause
- Categorizes cause (input_validation, output_encoding, etc.)
- Identifies contributing factors from evidence
- Attempts to locate code location from process traces

## Remediation

Generated by `RemediationService`:
- Template-based per vulnerability type
- Includes root cause action if available
- Each action has verification steps
- Tied to evidence through root cause

## Regression Tests

Generated by `RegressionTestService`:
- Created per finding
- Includes input data, expected outcome, validation criteria
- Executed independently
- Results update finding status (FIXED/REGRESSION)

## API Operations

### Create Finding
```
POST /api/v1/findings/
{
  "target_id": "api.example.com",
  "attack_id": "sql_injection",
  "execution_id": "uuid",
  "vulnerability_type": "sql_injection",
  "evidence_ids": ["uuid1", "uuid2"]
}
```

### Transition Status
```
PATCH /api/v1/findings/{finding_id}/status
{"status": "CONFIRMED"}
```

### Add Remediation
```
POST /api/v1/findings/{finding_id}/remediation
{"actions": [...]}
```

### Add Regression Test
```
POST /api/v1/findings/{finding_id}/regression-test
{"test": {...}}
```

## Validation Rules

1. `evidence_ids` cannot be empty
2. All `evidence_ids` must exist and be valid
3. Status transitions must follow lifecycle
4. REMEDIATED requires remediation actions
5. REGRESSION_TESTED requires regression tests
6. Duplicate detection on creation
